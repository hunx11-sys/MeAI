```

                 ② 지급 규칙(rules.json)                 이름으로 보상 유형을 정하는 표 — 대부분 기존 규칙에 걸림
                 ③ 점검 하네스 H1~H5                     전 특약 × 전 칸 계산 · 오류 0 이어야 다음으로
                 ④ 설계서로 전후 비교(regress)            고친 곳만 달라졌는지
정보계 새 표 ──▶ ⑤ 담보코드 매핑(scripts/codemap)       단위상품코드 + 담보코드 → 특약 마스터 ID

                 ⑧ IT 인계 묶음 교체                     dist/ga_v2_generator_package.zip
```

- **반영 전에도 틀린 금액은 나오지 않습니다.** 처음 보는 담보는 계산에서 빼고 사유를 로그에 남깁니다(빈칸 원칙 · 아래 2).

## 2. 반영 전에 신담보가 든 설계서가 오면

2026-11-20 에 실제로 시험했습니다(11월 설계 한 건에 가짜 신담보 3개를 넣어 생성).

| 넣은 담보 | 결과 | 로그 |
|---|---|---|
| 규칙표에 없는 새 유형의 수술비 | 계산 제외 | `[미분류] … 규칙표에 해당 담보 유형이 없어 계산 제외 (rules.json 보강 필요)` |
| 약관 데이터에 없는 진단비 · 치료비 | 계산 제외 | `[KCD없음] … 특약 마스터에 없다 — 약관 KCD 목록을 붙일 수 없으므로 지급 판정 제외` |

- PDF 는 정상으로 만들어졌고, **기존 칸 값은 하나도 바뀌지 않았습니다**(바뀐 칸 0).
- 신담보 이름은 지면에 찍히지 않습니다. 생성 결과와 함께 나오는 로그 파일(`…_log.txt` · API 응답의 로그)에만 남습니다.
- 운영 제안 : 로그의 `[미분류]` · `[KCD없음]` 건수를 모아 보면 「아직 반영 안 된 담보」 목록이 됩니다. 이 목록이 업데이트 요청의 시작점입니다.
- **주의(2026-11-23 실제 사례)** : 신담보라도 **이름이 기존 담보와 비슷하면 기존 규칙에 걸려 계산될 수 있습니다.** 새 상품 약관 27개를 받아 보니 「종합병원 전신마취(1시간초과) 수술비(1-7종)」 은 일반 1-7종 수술비로, 「중증뇌경색증진단비」 는 뇌경색 진단만으로 가입금액이 계산될 수 있었습니다(지급 조건이 다릅니다). 그래서 **새 상품 약관을 받으면 ① 기존에 없던 담보 이름을 먼저 뽑아 ② 「약관 검수 전 계산 제외」 규칙(`rules.json > skip_new_2611`)에 올리고 ③ 약관을 검수한 담보부터 제 규칙을 붙입니다.** 처음에는 93종(올케어 뇌심 · 수술비 · 골키퍼 · Only You 통합 · 상해안심의 신담보)을 올렸고, **1차 검수(v9.08 · 2026-11-23)로 의료 담보 90건 중 23종(33건)은 약관 대조를 마쳐 계산을 붙였습니다.** 14종(40건)은 약관 조건(중증도 점수 · 마취 시간 · 연간 횟수 등)을 사례로 단정할 수 없는 조건부 담보라 빈칸으로 확정했고(`skip_new_cond`), 7종(17건)은 수가코드 · 분류표 정리가 남아 대기입니다(`skip_new_2611`). 목록은 `dist/ga-v2-new-riders-pending-2611.xlsx`. 빈칸인 담보는 로그에 사유가 남습니다.
- **검수 한 건의 순서(1차 검수에서 실제로 한 일)** : ① 약관 제1조(지급사유 · 지급금액표) · 정의 조항을 읽는다 ② 별표(분류표)를 원문과 한 줄씩 대조한다 — 「제외」 가 대상 코드로 들어가지 않았는지 꼭 본다(1차 검수에서 세 가지 꼴을 찾아 추출기를 고쳤습니다) ③ 규칙에 붙인 뒤 **대상 사례 · 대상 아닌 사례 · 제외코드 · 병원 종별**을 직접 넣어 지급 경로를 확인한다 ④ 기존 담보의 규칙이 하나도 안 바뀌었는지(마스터 이름 · 정보계 이름 전부) · 설계 18건 값이 그대로인지 본다 ⑤ 정보계 전 줄 계산 대조 · 인쇄 검증.

## 3. 무엇이 바뀌면 무엇을 고치나

| 바뀐 것 | 고치는 곳 | 자동 / 사람 | 걸리는 일 |
|---|---|---|---|
| 약관 판 변경(예 2610 → 다음 판) | 약관 PDF 교체 → 마스터 다시 추출 | 자동(추출기) + 바뀐 질병코드는 사람이 약관으로 한 번 더 확인 | `fetch_terms.py --write` → `sync_all.py` |
| 신담보 — 기존 유형(진단비 · 수술비 · 일당 · 통합치료비 항목 등) | 마스터에 자동으로 들어옴 · 규칙은 기존 것에 걸림 | 자동 | 하네스 통과만 확인 |
| 신담보 — 새 유형(지급 조건이 기존 규칙에 없음) | `rules.json` 에 규칙 한 줄(약관 조문 근거) | 사람(세일즈혁신) | 약관 확인 → 규칙 추가 → 하네스 · 전후 비교 |
| 신담보 — 종 · 등급별 금액(분류표가 따로 있는 수술비) | 분류표 추출기(예 `extract_polyp6.py`) + 규칙 | 사람 | 약관 표를 칸 선으로 읽어 json 으로 |
| 기존 담보 이름 변경 | 마스터 재추출로 반영 · 정보계 이름과 다시 맞춤 | 자동 + 매핑 다시 | `sync_all.py` → codemap |
| 판매중지 담보 | 마스터에서 삭제 → 옛 설계서에 있으면 빈칸 + 로그 | 자동 | 판 변경 절차에 포함 |
| 정보계에 새 담보코드 · 새 단위상품코드 | 담보코드 매핑(codemap) 다시 | 자동 판정 + 「확인 필요」 는 사람이 결정 | 4장 |
| 디자인만 변경(표 · 구조 같음) | 틀 · CSS | 계산과 무관 | `DESIGN_SWAP.md` |
| 지면 칸 추가 · 삭제(구조 변경) | `ga_spec.py` 칸 정의 · 값 자리 · 설계도 | 사람 | 칸 사례(질병코드 · 수술 · 병원)는 약관 · GA 확정 뒤 |

주요수술 카드 다섯 줄 배정은 이름 규칙(`ga_v2.grp_of`) 한 곳입니다. 새 수술비 특약은 고치지 않아도 줄이 정해지고, 어느 줄에도 해당하지 않으면 「그 외 수술비」(골절 카드는 「골절수술비 및 그 외 수술비」)로 갑니다(소유자 확정 2026-11-20).

## 4. 신담보 반영 순서(세일즈혁신이 하는 일)

저장소 `CLAUDE.md` 의 「새 상품 · 신담보 · 새 약관을 넣을 때」 와 같습니다. 전부 통과할 때까지 3 ↔ 4 를 돕니다.

1. **약관 PDF 올리기** — GitHub 릴리스 「약관 올리는 곳」에 zip 으로. `python3 scripts/fetch_terms.py --write` 가 받아 옛 판을 바꿉니다.
2. **마스터 추출** — `python3 scripts/sync_all.py` (tool.html → db.json · 약관 → db_terms_extra.json · 하네스 · 세일즈북 · 배포판을 한 번에).
   끝나면 「신규 N · 삭제 N · 질병코드 바뀜 N」 요약이 나옵니다. 질병코드가 바뀐 특약은 약관 원문으로 한 번 더 확인합니다.
3. **점검 하네스** — `cd proposal_smart && python harness.py --designs <설계서 폴더>`
   - H1 마스터 무결성 · H2 규칙 미분류 0 · H3 이름 꼬리표 · H4 전 특약 × 전 칸 계산 · H5 금액 상식 · H6 설계서 지면 대조
4. **실패 항목만 고치기** — H2 실패(규칙 없음) → 약관 조문을 읽고 `rules.json` 에 규칙 추가. 조건을 사례로 단정할 수 없으면 「계산 제외 + 사유」 규칙으로 둡니다(틀린 금액보다 빈칸).
5. **전후 비교** — `python regress.py snap before / after` → `diff`. 고친 곳만 달라지고 나머지는 글자 차이 0쪽이어야 합니다.
6. **기록** — `api.py` VERSION 올림 · `README.md` 맨 위에 무엇이 왜 얼마에서 얼마로 바뀌었는지 · 규칙 검수표 다시 뽑기.
7. **설계도 다시 뽑기** — `ga_docs/README.md` 순서(GA 설계도 · 칸 지도 · 새양식 시트) + 5장의 담보코드 설계도.
8. **검증 두 가지**
   - `python3 verify_v2.py <설계서 폴더>` — 완성 PDF 의 글자를 다시 읽어 계산 값과 대조(쪽마다 · 전부 통과여야 함)
   - `python3 scripts/codemap/verify_designs.py …` — 담보코드로 찾은 특약 = 설계서 이름으로 찾은 특약 · 계산 값 차이 0
9. **묶음 교체** — `python3 scripts/build_ga_v2_package.py` → `dist/ga_v2_generator_package.zip` 을 IT 에 전달.

## 5. 담보코드 매핑 업데이트(IT ↔ 세일즈혁신)

정보계는 담보를 「단위상품코드 + 담보코드」로 가리키고, 우리 계산은 특약 마스터 ID 를 씁니다. 그 사이를 잇는 표가 **담보 식별표**(담보코드 설계도 시트 4)입니다.

**IT 가 주는 것** : 정보계 「단위상품코드 · 담보코드 · 상품담보명」 표 최신판(엑셀). 신담보 판매개시 전에 받으면 판매 첫날부터 반영됩니다.

**세일즈혁신이 하는 일**(`scripts/codemap/README.md`)

```
python3 extract_rows.py <정보계 엑셀> <작업폴더>
python3 toc.py <작업폴더>
python3 run2.py <작업폴더>
python3 build.py <작업폴더> <매핑 엑셀>
python3 build_blueprint.py <작업폴더> <매핑 엑셀> <GA 결과 json> <설계도 엑셀> <v2data.json> <왕복 검증 json>
python3 verify_designs.py <작업폴더> <매핑 엑셀> <설계서 폴더> <왕복 검증 json>
python3 export_code_map.py <작업폴더> <매핑 엑셀> <code_map.json>              # 담보코드 입력이 쓰는 담보 식별표(사내 자료 · 서버에 GA_CODE_MAP 으로)
python3 verify_code_input.py <작업폴더> <매핑 엑셀> <설계서 폴더> <결과 폴더> --pdf   # PDF 로 넣은 결과 = 담보코드로 넣은 결과
python3 audit_rows.py <작업폴더> <code_map.json> <결과 json>                      # 정보계 전 줄 계산 대조(이름 길 = 담보코드 길 · 표기 변형 · 갱신형 유무 — 다른 곳 0)
```

**판정 단계** — 코드마다 자동으로 붙습니다.

| 단계 | 뜻 | 처리 |
|---|---|---|
| ① 정확 | 이름이 글자까지 같다 | 자동 연결 |
| ② 세부표기 | 괄호 · 순서 · 줄임 표기만 다르다 | 자동 연결 |
| ③ 특약단위 | 정보계는 세부보장(종별 · 암종별)마다 코드, 우리는 특약 하나 | 자동 연결(이름의 [질병3종] 등으로 종을 읽음) |
| ④ 유사 · 확인 필요 | 비슷하지만 같은 특약인지 사람이 정해야 함 | **세일즈혁신이 약관으로 확인해 결정** |
| ⑤ 없음 | 우리 약관(14개 상품)에 없는 담보 · 대상 아닌 상품 | 계산 제외 + 로그(빈칸) |

2026-11-20 기준 : 정보계 코드 3,536개 중 3,095개 연결(① 2,218 · ② 446 · ③ 431) · 확인 필요 11 · 대상 아님 430.

**신담보가 나왔을 때 표가 어떻게 바뀌나**
- 새 담보코드 행이 정보계 표에 생김 → 4장 2번까지 끝난 뒤 codemap 을 다시 돌리면 새 행에 특약 마스터 ID 가 붙습니다.
- 약관이 아직 반영되지 않은 코드는 ⑤ 없음으로 남고, 그 담보는 계산 제외 + 로그입니다. 약관을 넣고 다시 돌리면 연결됩니다.
- 담보코드와 이름은 1:1 이 아닙니다(한 코드가 상품마다 다른 이름). **반드시 「단위상품코드 + 담보코드」 짝으로** 찾습니다.

**왕복 검증**(2026-11-20 · 11월 설계 18건 · 담보 980개)
- 같은 특약 716 · ID 는 다르지만 약관 자료(질병코드 · 제외코드 · 수가코드)가 같음 257 · 자료가 다른 특약 6 · 엔진이 못 찾은 담보 1(보호자 일반상해사망 — 칸에 들어가지 않는 담보)
- 코드 길로 찾은 특약 자료로 다시 계산 → **18건 × 칸 144개 모두 같은 값(다른 칸 0)**
- 자료가 다른 6건은 부모 특약 ↔ 세부보장 차이이고, 지급 판정은 이름의 세부보장 글자로 하므로 금액에 영향이 없음을 계산으로 확인했습니다(담보코드 설계도 시트 12).

## 6. IT 가 스마트 제안서를 돌리는 두 가지 방식

| | A. 프로그램 그대로(설계서 PDF 입력) | B. 전산이 담보 목록을 직접 넘김(담보코드 입력) |
|---|---|---|
| 지금 있는 것 | 있음 — `dist/ga_v2_generator_package.zip` (웹 서버 + API `/v1/ga2/pdf`) | **있음(v9.06)** — 같은 묶음의 API `/v1/ga2/json/pdf` · `/all` · `/check` · 명령줄 `python ga_v2.py --json` · 모듈 `code_input.py` |

## 8. 받는 쪽 인수 시험(IT)

묶음을 받은 자리에서 아래 셋이 통과하면 교체합니다.

```
python harness.py                          # H1~H5 「결과 : 전부 통과」
python verify_v2.py <설계서 폴더>           # 「결과 : 전부 통과」 — 지면에 찍힌 값 = 계산 값
python regress.py snap … / diff            # 앞 판 묶음과 비교해 변경 기록에 적힌 곳만 달라졌는지(선택)
```

- `verify_v2.py` 는 완성된 PDF 의 글자를 다시 읽어 보장요약 · 암 · 뇌 · 심 · 수술 카드 · 간병인 표 · 세부내역을 계산 값과 대조합니다(설계 1건에 500~800곳).
  일부러 틀린 값을 넣는 시험에서 쪽 종류마다 모두 잡아냈습니다(2026-11-20).
- 설계서 PDF 는 개인정보가 있어 묶음에 넣지 않습니다. 시험은 받는 쪽 설계서로 합니다.
