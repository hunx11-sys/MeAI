# 스마트제안서 자동 삽입 모듈(proposal_smart v8.2) 검수 보고서

검수 일자: 2026-09-15
검수 대상: `proposal_smart_code_v8.zip` (21개 파일, base64 사본과 md5 동일) · 44세 여성 The건강한 5.10.5 결과물 PDF(65쪽) · `smart_proposal_44F_audit.json`
검수 질문: ① 현재 결과물에 오류가 있는가 ② 다른 상품·특약이 들어와도 위화감 없이 구조가 유지되는가

## 0. 검수 방법

업로드된 65쪽 PDF는 이미 모듈이 만든 **결과물**(원본 56쪽 + 생성 9쪽)이었다. 그래서 다음 순서로 재현 검증했다.

1. 결과물에서 생성 9쪽(44~52쪽)을 떼어 원본 56쪽을 복원
2. 복원한 원본으로 `build_all.py`를 끝까지 실행 → 65쪽 결과물 재생성
3. 재생성한 9쪽의 텍스트를 업로드본과 대조 → **9쪽 전부 동일**(발행시각 제외), 감사 로그 `_audit.json`도 **완전 일치**
4. 규칙표(rules.json)에 특약 마스터 951건 전수 대조, 의심 지점은 엔진을 직접 호출해 재현
5. 스트레스 테스트: 담보 5건 소형 설계 · 운전자 전용 60건 · 치아 전용 49건 · 마스터 951건 전체 · 40M 통합간편(cust_a) · 40F The건강한(cust_b)을 각각 9쪽으로 렌더링해 지면 확인

실행 환경 메모: 이 모듈은 실제로 돌리려면 Python 3.12 이상, Playwright용 Chromium, 나눔고딕·Healthicons(`fetch_assets.py`), 로고 추출용 poppler(`pdfimages`)가 필요하다. README에는 이 요구사항이 적혀 있지 않다.

## 1. 결론 요약

- **현재 44F 결과물의 숫자는 코드 논리대로 정확히 재현된다.** 담보 151건 인식, 규칙 분류 미분류 0건, 통합암진단비 세부급부 그룹 판정(위암→특정소화기암만 지급), 표적항암 1종/2종 이상 열의 차액(8,000만원 = [2종이상] 3,000 + 암진단및치료비Ⅱ[표적 2종및3종이상] 5,000) 등 표본 계산이 모두 맞았다.
- 그러나 **"어떤 상품·설계가 와도 오류 없이 동작"이라는 README의 주장은 그대로 받아들이기 어렵다.** 아래 A그룹 6건은 다른 설계에서 금액이 틀리거나 담보가 조용히 사라지는 실제 결함이고, B그룹 10건은 다른 상품에 붙였을 때 고객이 바로 느낄 위화감이다.
- 가장 큰 구조 문제 두 가지: **(1) 통합치료비를 이름 9종에 고정 매핑**한 부분, **(2) 9쪽 고정 구성**. 이 둘을 고치지 않으면 운전자보험·치아보험·통합치료비 변형 담보가 들어오는 순간 결과물이 어색해지거나 틀린다.

## 2. A그룹 — 즉시 수정이 필요한 오류 (재현 완료)

### A-1. `gen2.py`가 Python 3.11 이하에서 실행 자체가 안 된다
- 303행의 f-string 안에 `\"`(백슬래시)가 들어 있어 3.11에서 `SyntaxError`로 즉시 중단된다. 3.12 이상에서만 컴파일된다.
- 다른 6개 모듈은 3.11에서 문제 없음. 회사 PC·서버 파이썬이 3.12 미만이면 첫 실행부터 실패한다.
- 수정: 문자열 상수를 f-string 밖으로 빼기(예: `NOP2 = '<span class="nop2">미가입</span>'` 선언 후 `{c["v"] if c["on"] else NOP2}`). README에 요구 버전 명시.

### A-2. 통합치료비 담보가 이름 9종에 고정되어 있어, 변형 담보는 오계산 또는 무시된다
`scen_engine.ITC_MAP`에 통합치료비 9종 이름만 등록되어 있고, `itc_id()`의 고지유형 꼬리표 제거 목록은 3종뿐이다. 마스터에는 통합치료비가 29건, 약관 금액표(`product_data.json`)에는 12종(ca_basic_c·ca_lite_c·ca_ncm_c 포함)이 있다.

| 입력 담보명 (가입금액) | 실제 동작 | 결과 |
|---|---|---|
| 암 통합치료비(기본형)(통합간편심사형) 1억 | 통합치료비로 인식 못 함 → 규칙표 마지막 `tx_etc_care`로 떨어짐 | **암 진단 시 1억원 정액 지급으로 표기** (오계산) |
| 암 통합치료비(기본형)(암중점치료기관(상급종합병원 포함)) 1억 | 같은 경로, 그러나 진단·수술 어느 시나리오에서도 0원 | **모든 지면에서 조용히 사라짐, 로그 없음** |
| 상해 통합치료비(실속형) | itc 없음 → `tx_etc_care` | 상해 예시에서는 gen2가 별도 `inj_itc.json`으로 처리해 다행히 표시되지만, 엔진 관점에서는 미인식 |

- 원인: 통합치료비 판정이 데이터(마스터의 `c: integrated` 카테고리, product_data의 RIDERS)가 아니라 코드 안의 이름 사전에 있다.
- 수정: ① `itc_id`를 마스터 카테고리(`integrated`) + product_data RIDERS 이름으로 판정 ② 통합치료비인데 금액표에 없는 담보는 `tx_etc_care`로 흘러가지 못하게 규칙표 앞쪽에 `kind: itc_unknown`(계산 제외 + 로그) 규칙 추가.

### A-3. 가입금액 표기에 따라 담보 행이 통째로 사라진다 (로그 없음)
`matcher.read_proposal`의 금액 정규식과 `scen_engine.amt_to_man`이 다음 표기를 인식하지 못한다.

| 표기 | 담보 리스트 인식 | 만원 환산 |
|---|---|---|
| 1억5천만원 | 실패 → **행 자체 누락** | 0 |
| 1억 5천만원 | 실패 | 0 |
| 3천5백만원 | 실패 | 0 |
| 1억 | 실패 | 10000 |
| 1억5,000만원 | 실패 | 15000 |

- 누락된 담보는 감사 로그에도 남지 않아 "담보 N건 인식"만 보고는 알 수 없다. 사망·후유장해 1억5천만원 설계에서 바로 발생한다.
- 수정: 금액 파서를 하나로 통합해 `억·천·백·십·만` 조합을 전부 처리하고, 원본 표에서 번호가 있는데 인식하지 못한 행은 `검토필요` 로그로 남길 것.

### A-4. 규칙 순서 충돌 — 16대특정암진단비가 마스터 KCD가 있어도 0원
- `dx_cancer_group`의 정규식 `\d+대특정암`이 `16대특정암진단비`를 먼저 잡아 `kcd_groups`(별표13 4그룹)에서 찾고, 목록이 없어 "분류표 없음"으로 제외한다. 마스터(db.json)에는 이 담보의 약관 KCD 34개가 있는데 쓰이지 않는다.
- 수정: `dx_cancer_group`의 정규식을 `(특정소액암|특정소화기암|14대특정암|10대특정암|4대고액암)`처럼 별표13 그룹명으로 한정하거나, `group` 모드에서 목록이 없으면 `codes`로 폴백.

### A-5. 고지유형 꼬리표 정규식이 세 곳에 서로 다르게 정의되어 있다
- `matcher.GOJI`(8종) · `scen_engine.GOJI`(9종, `통합간편심사형` 포함) · `scen_engine.itc_id` 내부(3종). 새 고지유형(예: 3.2.5간편가입, 유병자가입)이 나오면 세 곳을 모두 고쳐야 하고, 한 곳만 빠지면 A-2 같은 오계산이 생긴다.
- 수정: 상수 하나로 통합(`rules.json`에 `goji_tags` 배열로 두면 코드 수정 없이 추가 가능).

### A-6. 담보명이 같고 갱신주기만 다른 담보는 한 건이 사라진다
- `read_proposal`은 `base(name)`으로 중복 제거하는데 `base()`가 `(10년갱신)`·`(20년갱신)`을 지운다. 따라서 `(10년갱신)갱신형 간병인사용일당(1일이상)`과 `(20년갱신)갱신형 간병인사용일당(1일이상)`이 같은 키로 묶여 **둘째 행이 탈락**한다. 1-7종 수술비 하위행(`┗ 수술비[질병1종]`)이 갱신형·비갱신형 두 부모 아래 반복될 때도 같은 일이 생긴다.
- 수정: 중복 키를 `(번호, base)`로 하거나 부모 담보명을 하위행 키에 포함.

## 3. B그룹 — 다른 상품·특약에 붙일 때 생기는 위화감 (구조)

### B-1. 9쪽 고정 구성 — 담보가 없어도 빈 지면이 그대로 나간다 (→ v8.4에서 조건부 구성으로 해소, 4-1절 참조)
스트레스 테스트 결과(모두 정확히 9쪽 생성):

| 설계 | 지면 상태 |
|---|---|
| 담보 5건(사망·암진단·질병수술·입원일당·벌금) | 통합치료비 쪽은 "통합치료비 담보 미가입" 한 줄 뒤 **전체 여백**, 암 쪽은 항암·방사선 표가 전부 0만원, 사례 쪽은 "해당 담보 없음" 반복 |
| 운전자 전용 60건 | 한장요약 진단 3카드 0원·수술 0원·간병 미가입, 암/뇌심/질병코드지도/통합치료비/다빈도/사례 **7쪽이 전부 0 또는 미가입** |
| 치아 전용 49건 | 같은 양상 |

- 원인 두 가지: `gen2.py`가 페이지 목록 `P`를 항상 9개로 만들고, 쪽번호 계산도 `NEW = 9`로 하드코딩. `build_all.py`는 실제 생성 PDF 쪽수를 다시 세지만 `.page{overflow:hidden}` 때문에 항상 9쪽이 되어 두 값이 우연히 일치할 뿐이다.
- 수정(v8.4 반영): 쪽별 표시 조건을 두고 없는 계열의 지면·블록을 빼며 쪽번호를 실제 생성 쪽수로 계산. 운전자·치아처럼 암·뇌·심장·통합치료비가 전혀 없는 단일상품은 대체 지면을 만들지 않고 **스마트제안서를 붙이지 않는다**(원본 그대로).

### B-2. 한장요약 지면 한도와 "조용한 잘림"
- 151건 설계는 하단 여백 26pt로 겨우 들어갔다. 951건에서는 담보 목록이 면책문구·발행정보 위로 넘쳐 겹쳐 인쇄된다(레이아웃 검사에 `이탈` 8건 검출).
- 문제는 검출되어도 **빌드가 계속 진행되어 결과물이 그대로 나온다**는 점. 44F 정상 출력물에도 사례 쪽 담보명 말줄임 8건이 `잘림`으로 찍혀 실제 문제와 구분되지 않는다.
- 수정: `이탈`은 빌드 실패(또는 자동 2쪽 분할), 말줄임(`text-overflow: ellipsis`)은 검사에서 제외.

### B-3. 한장요약 진단 카드가 특정 질병코드 하나로 계산된다
- 암 진단 7,000만원은 **위암(C16) 기준**, 뇌혈관 4,000만원은 뇌경색(I63), 심혈관 4,000만원은 급성심근경색(I21) 기준이다. 카드 문구는 "암(유사암제외) 진단확정 시"라 모든 암이 7,000만원처럼 읽힌다.
- 44F 설계로 암종별 진단비 합계를 돌려 보면 위암·폐암·유방암·간암·췌장암은 7,000만원이지만 **신장암(C64)은 2,000만원**이다(10대특정암 분류표 미확보 영향 포함).
- 수정: 카드에 기준 질병 표기("위암 기준") 또는 최소~최대 범위 표기.

### B-4. 세부급부 행의 가입금액 단순 합산과 동일 표기 반복
- 한장요약 "암 51개 · 합계 16억 8,820만원"은 26종 항암방사선및약물치료비의 암종별 급부 26행(각 4,000만원, 서로 배타적)을 그대로 더한 값이다. 이런 합계는 고객에게 과장된 인상을 준다.
- 80건 초과 시 담보명을 19자로 자르므로 같은 "26종 항암방사선및약물치료비(전이포" 가 26줄 반복된다. 세부급부는 부모 담보 1행 + "세부 26개"로 접는 것이 자연스럽다.

### B-5. 26종 항암방사선및약물치료비 암종 판정이 시뮬레이터 동의어 사전에 의존
- 암종→KCD 변환에 통합치료비 시뮬레이터의 `EMB.syn`(병명 동의어 42개)을 쓰고 있어 두경부암·간담췌암·혈액암·생식기관암 등 **26개 급부 중 18개가 계산 제외**된다(감사 로그와 일치).
- 위암·폐암 사례에서만 우연히 값이 나오고, 다른 암종 사례를 넣으면 대부분 0원이 된다.
- 수정: 통합암진단비 별표13처럼 26종 분류표를 `rules.json kcd_groups`로 옮겨 `group` 모드로 판정.

### B-6. 마스터 KCD 공백
- `db.json` 951건 중 471건은 약관 KCD 목록이 비어 있다. `kcd: codes` 규칙에 걸리는 담보의 절반은 "KCD없음" 로그로만 남는다. 특약검색기(tool.html) 데이터 보강이 선행되어야 한다.

### B-7. 지면 세부 위화감
- 상단 헤더의 상품명 줄 글꼴이 원본보다 작다(43쪽과 44쪽 비교).
- 피보험자명이 "고객님"으로 들어오면 제목이 **"고객님 고객님 보장 한장요약"**이 된다.
- 수술비 쪽 "질병군별 추가 수술비" 라벨에 담보명 끝 괄호를 그대로 쓰기 때문에 `연간1회한`, `심장,뇌혈관,신부전,간,폐` 같은 문구가 질병군 이름 자리에 나온다(951건 테스트에서 확인).

### B-8. 쪽번호 덮어쓰기 방식
- 시각적으로는 정상이다(53/65로 보임). 그러나 흰 사각형으로 덧칠만 하기 때문에 텍스트 레이어에는 옛 번호가 남아 `4543//5665`처럼 읽힌다. PDF 검색·복사·스크린리더·다른 시스템의 재처리에서 그대로 노출된다.
- 원본 쪽번호가 `N/총쪽수` 한 단어로 추출되지 않는 양식(띄어쓰기, "Page N of M")이면 재부여가 조용히 건너뛰어진다.
- 대안: 원본 쪽번호는 두고 삽입 쪽만 `43-1 … 43-9`식 부번호를 쓰거나, 설계시스템이 PDF를 만들 때 쪽번호를 마지막에 찍는 방식으로 협의.

### B-9. 삽입 위치 판정이 문구 하나에 의존
- "보장보험료 합계"가 마지막으로 나오는 쪽을 담보사항 끝으로 본다. 이 상품에서는 3쪽과 43쪽에 나와 43쪽(상세표 끝)이 맞게 잡혔지만, 문구가 없으면 3쪽 뒤에 끼워 넣는 고정값으로 떨어진다. `auto_meta`는 원본이 3쪽 미만이면 예외로 중단된다.
- 수정: "담보사항" 표 헤더가 있는 마지막 쪽을 기준으로 삼고, 판정 근거를 감사 로그에 남길 것.

### B-10. 상품 라인 추정과 매칭 신뢰도
- `guess_line`은 통합간편/케어프리 둘만 구분하고 The건강한·운전자·치아는 케어프리로 간주한다. 이름이 같아 대개 문제없지만 상품별 KCD 차이가 있는 담보는 다른 상품 약관으로 판정될 수 있다.
- 완전일치·괄호 제거·최장 접두 일치가 모두 `matched: true`로 기록되어 어느 단계에서 맞았는지 알 수 없다. 매칭 방식(exact/paren/prefix)을 행에 남기면 검수가 쉬워진다.
